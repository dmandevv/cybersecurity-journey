# 1.1 — Compare and contrast various types of security controls.

**Domain 1 — General Security Concepts** · 12% of the exam · **12 terms** from the official objectives.

Every term below is quoted from the SY0-701 objectives document, version 7.0. Tick a box once the term can be explained without looking, and write the explanation underneath it.

- [x] **Categories**
  - [x] Technical
    - A control done automatically by a computer — on a timer, when a condition is met, or in response to another action. **Example:** the homelab heartbeat. I wrote the script and the cron job, but the server schedules and runs it.
    - *Refinement:* the test is **what enforces it**, not whether a human is involved — an MFA prompt needs a person to type a code, but the system decides whether they get in. Also called *logical* controls.
  - [x] Managerial
    - Decides what needs to be done in a situation and how to do it. **Example:** the homelab new-host checklist line *"Timezone is UTC"* — the rule. `timedatectl set-timezone UTC` is the technical control that enforces it.
    - *Refinement:* it does nothing on its own — policy, procedure, plan, risk assessment, standard. Also called *administrative*. Watch for the pairing: password **policy** = managerial, system **enforcing** length = technical.
  - [x] Operational
    - Work done manually by people — in response to technical controls (alerts) or to ensure compliance (managerial). **Example:** masking RouterOS export headers by hand before every commit. The rule is managerial; the pre-commit hook that replaced the manual step is technical.
    - *Refinement:* categories describe the **control doing the protecting**, not every task around it — writing the hook was building a technical control, not an operational one. Test: *if the person stops, does the protection stop?* Guards, delivering training, log review, alert triage.
  - [x] Physical
    - Protects by physically limiting access — the door existing blocks someone from walking in. **Examples** between a stranger and my Dell: the building's door FOB, cameras on the entrances, the building door itself. A business adds locks on its server racks.
    - *Refinement:* **limits or monitors** physical access — a camera blocks nothing but still counts. Category ≠ type: a camera is *physical* and *detective*; a badge reader is *physical* even though a computer checks the badge. Layers of them = defense in depth (1.2).
- [x] **Control types**
  - [x] Preventive
    - Stops things from happening in the first place. **Example:** firewall rules limiting what the desktop is allowed to reach on the LAN — technical.
    - *Refinement:* test is *does the bad thing get through?* Same traffic can change type by decision: `PLAIN-DNS` **drop** = preventive; `DoH NOT WORKING` **log-only** = detective. Preventive controls can be bypassed — the other types exist to cover that gap.
  - [x] Deterrent
    - Protects only by a warning with an apparent threat of consequences — if someone doesn't notice the warning, it is useless. **Example:** an SSH login banner — technical, since the system displays it every time.
    - *Refinement:* the warning can be implied by **presence** — visible guards, lighting, a camera on the wall. A banner's purpose isn't disclaiming responsibility: it states *monitored, unauthorized access prosecuted* — deters, and gives legal notice so an intruder can't claim they didn't know. Locked door = preventive; sign on the door = deterrent. Visible camera: "discourage" → deterrent, "identify afterwards" → detective.
  - [x] Detective
    - Makes you aware of something — acting on it is a separate issue. **Example:** the switch's default deny on input and forward has a **log** rule (detective) next to the **drop** rule (preventive).
    - *Refinement:* together the pair is both types — one control can be more than one type. Order matters: `drop` is terminating, so a log rule *below* it never fires (audit 2 finding). A detective control is only as good as whoever reads it — see the 2026-09-13 incident. IDS, SIEM rules, cameras recording, audits, drift checks.
  - [x] Corrective
    - Fixes or reverts damage done, after the event. **Examples:** `restart: unless-stopped` on the website container → technical; `AcPwrRcvry = On` → technical; `recovery.md` → managerial (and following it during a lockout → operational).
    - *Refinement:* some corrective controls are the plan, some do the fixing themselves — both restore to normal. Timeline: preventive (stop) → detective (know) → corrective (fix). Backups/restore, post-exploit patching, AV quarantine, failover.
  - [x] Compensating
    - A bandaid solution for something that can't be fixed normally. **Example:** NIC offloads disabled on the Dell — technical, done to compensate for Dell never shipping an `e1000e` firmware fix. Also corrective: it was the fix applied after the 2026-09-08 outage.
    - *Refinement:* not necessarily temporary or inferior — it must **reduce risk to an acceptable level**, with the remaining gap documented (PCI DSS accepts these formally). Homelab: UDP syslog is spoofable, so forward rules match `in-interface` + `src-address`. Exam cues: *cannot, legacy, not supported, budget, until.*
  - [x] Directive
    - Informs people so they can make the proper decision — more precisely, **tells them what they must or must not do**, and relies on them following it. **Examples:** `daily-routine.md`'s "DO NOT EDIT THIS FILE"; the homelab README's "enable the hook after cloning" (the technical control only works if the directive is followed first).
    - *Refinement:* sign on a server room door — "Doors must remain closed at all times" = **directive**, "Violations will be reported to management" = **deterrent**; category **physical** (signage), not managerial — the policy behind it is managerial, the sign on the door is physical. Directive = *do this*; deterrent = *or else*.
